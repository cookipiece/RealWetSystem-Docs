# 성능

<ProductName />은 Unity에서 젖음을 미리 계산하고, VRChat 안에서는 셰이더가 그 결과를 그립니다. 이 페이지에서는 업로드 용량, 빌드 시간, 인게임 부하를 차례로 설명합니다.

## 업로드 용량 {/* #upload-size */}

젖는 머티리얼마다 젖음용 셰이더와 데이터가 아바타에 들어가므로, 업로드 용량이 늘어납니다.

| 늘어나는 것 | 크기를 정하는 것 |
| --- | --- |
| 젖음 셰이더 | 젖는 머티리얼의 수. 머티리얼이 많을수록 커집니다. |
| 젖음 데이터(젖는 위치, 보호 마스크, 몸에 닿는 정도) | 젖는 메쉬의 정점 수와 보호 영역 |
| 인게임 메뉴 아이콘 | 메뉴에 넣은 항목 수 |
| RealRain 비 데이터 | RealRain과 함께 쓸 때, 비를 받는 옷의 정점 수 |

- <strong>의상마다 고르게 젖어 보이게 (새 외형)</strong>은 기본으로 켜져 있으며, 업로드 용량을 조금 더 늘립니다.
- 아바타의 용량 한도에 가깝다면, 젖을 필요가 없는 파츠(장신구, 신발 등)의 **젖음 기능 사용**을 꺼 주십시오. 꺼진 파츠는 젖음 처리에서 빠집니다.

### 예시 측정값

아래는 예시 아바타 하나에서 잰 대략적인 값입니다. 업로드에 들어간 젖는 머티리얼 칸이 약 100개(렌더러 145개)이고 d4rk Avatar Optimizer를 켠 아바타를, 출시 전 <ProductName /> 1.0.0 빌드로 쟀습니다. 「없음」은 같은 빌드에서 <ProductName />만 뺀 결과입니다.

|  | 비압축 (VRChat PC 500 MB 한도 기준) | 압축 (LZ4, 다운로드 크기에 가까움) |
| --- | --- | --- |
| <ProductName /> 없음 | 380.7 MiB | 162.6 MiB |
| <ProductName /> 있음 | 412.6 MiB | 183.6 MiB |
| 차이 | +31.9 MiB | +21.0 MiB |

VRChat은 비압축 크기를 PC 한도와 비교하고, 다른 사람이 내려받는 크기는 압축 크기입니다.

늘어난 비압축 31.9 MiB는 다음과 같이 나뉩니다.

| 항목 | 늘어난 양 |
| --- | --- |
| 셰이더 | 23.5 MiB (젖는 머티리얼 칸 하나당 약 0.23 MiB) |
| 메쉬 | 4.1 MiB |
| 텍스처 | 3.8 MiB |
| 애니메이션 | 0.9 MiB |
| 머티리얼 | -0.4 MiB |

- 의상 한 벌이 늘리는 양은 셰이더 말고도 그 의상의 텍스처와 메쉬에 따라 달라집니다.
- 이 값에는 <strong>의상마다 고르게 젖어 보이게 (새 외형)</strong>(기본 켜짐)과 새 메뉴 아이콘이 들어 있습니다.
- 값은 의상, 셰이더, 함께 쓰는 최적화 도구에 따라 달라집니다.
- VRChat의 업로드 용량 한도는 <ProductName />만이 아니라 아바타 전체에 적용됩니다.

## 빌드 시간 {/* #build-time */}

### 첫 빌드와 이후 빌드

| 상황 | 걸리는 시간 |
| --- | --- |
| 처음 빌드하거나 처음 미리보기할 때 | 젖음 셰이더를 만들고 Unity가 컴파일하므로 오래 걸립니다. 머티리얼이 많으면 수십 분이 걸릴 수 있습니다. |
| 같은 설정으로 다시 빌드할 때 | 첫 빌드에서 만든 셰이더 캐시를 재사용하므로, 젖음 셰이더 컴파일을 거의 모두 건너뛰고 훨씬 짧게 끝납니다. |
| 셰이더(Poiyomi·lilToon)나 <ProductName />을 업데이트한 뒤 | 바뀐 셰이더만 다시 준비합니다. 처음 한 번은 다시 오래 걸릴 수 있습니다. |
| 젖는 위치·영역·의상 형태를 바꾼 뒤 | 바뀐 의상만 다시 계산합니다. |

방송이나 녹화처럼 PC가 바쁠 때 첫 빌드를 하면 더 오래 걸립니다. 첫 빌드는 PC가 한가할 때 미리 해 두는 편이 좋습니다.

- 업로드 중에는 `RealWet: 의상 형상 계산 중 (3/22) · 의상 이름`처럼 <ProductName />의 단계와 순서, 의상 이름이 진행 표시로 나옵니다.
- 진행 표시가 오래 그대로라도 Unity가 CPU를 쓰고 있다면 셰이더를 컴파일하는 중입니다. 기다려 주십시오. [첫 빌드가 오래 걸림](./troubleshooting.mdx#long-first-build)을 확인해 주십시오.

### 미리 준비해 두기

- **Unity를 1분간 조작하지 않으면 자동 준비**가 켜져 있으면, 키보드·마우스 입력이 1분 동안 없고 Unity가 뒤로 가 있을 때 필요한 의상을 한 벌씩 준비합니다. 지금 입고 있는 의상부터 준비하고, `EditorOnly` 의상은 준비하지 않습니다.
- 바로 준비하려면 **RealWet > 의상 관리 > 필요한 의상만 준비**를 누릅니다. 준비가 끝난 의상과 진행 중인 의상은 건너뜁니다.
- **Hierarchy에서 꺼진 의상도 포함**을 켜면 옷장으로 꺼 둔 의상도 미리 준비합니다. 끄면 꺼진 의상은 업로드할 때만 준비합니다.

### 준비 결과를 저장하는 곳

| 저장하는 것 | 위치 |
| --- | --- |
| 젖는 위치·퍼짐 계산 | 프로젝트의 `Library/RealWet` |
| 젖음 셰이더 준비 결과 | `Assets/CookiTools/RealWetSystem/Generated` |

- Unity를 다시 켜도 조건이 같으면 재사용합니다. Unity를 다시 연 직후 의상 상태가 아직 점검하지 않은 것으로 보여도, 캐시가 사라졌다는 뜻은 아닙니다.
- 캐시가 없거나 손상되면 필요한 계산을 다시 합니다. 캐시 파일을 직접 고치거나 폴더를 먼저 지울 필요는 없습니다.

### 재생(Play)할 때

재생 버튼을 누를 때 입고 있는 의상 중 아직 준비되지 않은 의상이 있으면, <ProductName />이 재생을 잠시 기다리게 하고 그 의상을 준비합니다.

- 기다리는 동안 Game 창과 Scene 창에 <strong>의상 N벌을 준비하고 있습니다. 끝나면 재생이 자동으로 시작됩니다. 바로 재생하려면 재생 버튼을 한 번 더 눌러 주십시오.</strong>가 보입니다.
- 준비가 끝나면 재생이 자동으로 시작됩니다. 10분이 지나면 남은 의상이 있어도 재생을 시작합니다.
- 재생 버튼을 한 번 더 누르면 바로 시작합니다. 이때 준비되지 않은 의상은 그 재생에서만 젖지 않고, 재생을 끝내면 그 의상부터 준비합니다.
- Hierarchy에서 꺼 둔 의상(토글로 켜는 머리카락 등)도 재생 전에 준비합니다. 입고 있는 의상을 먼저 준비합니다. **Hierarchy에서 꺼진 의상도 포함**을 끄면 꺼 둔 의상은 기다리지 않습니다.
- 이번 Unity 세션에서 아직 그려 본 적이 없는 젖음 셰이더는 재생 전에 2개씩 나누어 먼저 컴파일합니다. 첫 재생 중에 셰이더를 한꺼번에 컴파일하지 않으므로 메모리를 훨씬 적게 씁니다. 이미 컴파일한 셰이더는 다시 컴파일하지 않습니다.
- 젖음 셰이더는 그 슬롯에서 쓰지 않는 기능을 빼고 컴파일합니다. 보이는 모습은 같고, 셰이더가 작아지고 컴파일이 빨라집니다.

## 인게임 부하

- 젖음은 미리 계산한 데이터를 셰이더가 읽어서 그립니다. 시작점과 보호 영역은 Unity 편집용이며, 인게임에 Collider, PhysBone, Contact를 추가하지 않습니다.
- 인게임 메뉴는 고른 항목만큼 동기화 파라미터를 씁니다. 새 설치의 추천 메뉴는 87비트, 모든 항목을 켜면 94비트입니다(VRChat 한도 256비트). 다이얼은 8비트, 토글은 1비트입니다. 자세한 표는 [인게임 메뉴](./usage/in-game-menu.mdx#sync-cost)에 있습니다.
- **의상별 편차 줄이기**를 켜고 <strong>최대 젖는 범위 (%)</strong> 다이얼을 메뉴에 넣으면, FX에 미리 계산한 보정 클립이 늘어납니다. 동기화 비트와 인게임 계산은 늘지 않습니다.

## 용량과 시간을 줄이는 방법

1. 젖을 필요가 없는 파츠는 **젖음 기능 사용**을 끕니다.
2. 쓰지 않는 인게임 메뉴 항목은 **RealWet > 인게임 메뉴**에서 빼고 **런타임 메뉴 적용 / 갱신** 후 다시 빌드합니다.
3. 첫 빌드 전에 **필요한 의상만 준비**로 미리 준비해 둡니다.
4. d4rk Avatar Optimizer를 쓴다면 셰이더를 다시 쓰는 설정을 꺼 둡니다. 젖는 파츠가 d4rk의 병합에서 빠지면 머티리얼 수가 늘어나기 때문입니다. 자세한 내용은 [호환성](./compatibility.mdx#optimizers)을 확인해 주십시오.
