## Install button is gray {/* #install-gray */}

In 1.0.0, the **Install** button turns gray in the cases below, and the window doesn't say why. From 1.0.1, the reason appears above the button, and the first case installs without unpacking.

| Cause | Fix |
| --- | --- |
| The avatar is the FBX (model file) placed directly in the scene. Unity treats such an avatar as a model it can't edit. | Save your scene first. In the Hierarchy, right-click the avatar → **Prefab > Unpack Completely**, then press **Refresh** in the setup window. |
| The **Avatar** field holds the prefab file from the Project window. | Click your avatar in the Hierarchy, then press **Detect** in the setup window. |
| Unity is in Play mode. | Stop Play and try again. |

If it is still gray, please send a screenshot of the whole Unity window, including the Hierarchy, through BOOTH messages.

## Scripts look broken, or the CookiTools menu is missing {/* #scripts-missing */}

If you imported the package but there is no **CookiTools** in the Unity menu bar, or the components on the `RealWet` object or your outfits show **Missing Script**, please check the following in order. Please don't delete the components that show Missing Script. They come back once the cause is fixed.

### 1. A required package is missing or too old {/* #scripts-packages */}

In VCC, open **Manage Project**, check these packages and update them to the latest version within the supported range.

| Package | Supported |
| --- | --- |
| VRChat Avatars SDK | 3.10.0 or later, below 4.0 |
| NDMF | 1.13.1 or later, below 2.0 |
| Modular Avatar | 1.14.0 or later, below 2.0 |
| VRCFury (if used) | 1.1436.0 or later |

- If a new major version (for example 2.0) is out, please check [Compatibility](./compatibility.mdx#requirements) before you update. With a version outside the supported range, the main part of <ProductName /> does not load.
- If VRChat Avatars SDK, NDMF or Modular Avatar is missing or outside the supported range, the **RealWet Dependencies** window opens once after you import the package or start Unity. It shows each package's state, such as **install required** or **update required**, and the supported range.
- The window has three buttons. If you haven't chosen a display language yet, it shows in English.
  - **Check Again**: checks again after you change packages.
  - **Copy Issue for Support**: copies the Unity and package versions. Nothing is sent automatically.
  - **VCC Help**: opens VRChat's VCC guide page.
- In this state, **CookiTools > RealWetSystem > Setup／Uninstall** shows the **RealWet — Install Compatibility Check** message instead of the setup window. Your avatar is not changed.
- If NDMF is not installed at all, the <ProductName /> components on the `RealWet` object and your outfits show Missing Script.
- <ProductName /> does not update packages automatically.
- This window does not check VRCFury. If you use VRCFury, please use 1.1436.0 or later. [VRCFury is too old](#vrcfury-old)

### 2. Another package has a red compile error {/* #scripts-compile-error */}

If any package has even one red compile error, Unity can't load newly imported tools. Then neither the menu nor the components work, and the window above doesn't open either.

1. Open **Window > General > Console**.
2. Find the first red error at the top.
3. Use the file path in the error to find which package it is, then update or remove that package.

The wording of the error hints at the cause. The error usually contains a name from that package; for example, `nadena.dev` is NDMF or Modular Avatar.

| Error wording | Meaning | What to do |
| --- | --- | --- |
| `does not contain a definition for …` | A package is older than the tool expects. | Update that package. |
| `The type or namespace name … could not be found` | A package that is needed is missing. | Install that package. |

**Case:** The Unity menu bar had no **CookiTools** at all, so neither the setup window nor the purchase activation window could be opened. The Console had one red error: `'ObjectPathRemapper' does not contain a definition for 'GetAllPathsForObject'` (CS1061).

- **Cause:** NDMF and Modular Avatar were old versions.
- **Fix:** Close Unity. In VCC (or ALCOM), open **Manage Project**, update **Non-Destructive Modular Framework** and **Modular Avatar** to the latest versions, then open the project again.

### 3. The project is not a Unity 2022.3 project for VRChat {/* #scripts-unity-version */}

Please use it in a Unity 2022.3 avatar project for VRChat, made with VCC.

### 4. Right after importing {/* #scripts-after-import */}

If red errors remain in the Console right after importing, please restart Unity once. [Updating over an earlier version](#updating) says the same.

### 5. Only part of the package was imported {/* #scripts-partial-import */}

If you unchecked some files in the import window, it may not work. Please import the `.unitypackage` again and press **Import** with every item checked.

Once it is fixed, **CookiTools** appears in the Unity menu bar. If this is the first time on this PC, please start with [Purchase activation](./license-activation.mdx).

If it still doesn't work, please send us the whole first red error in the Console and the package list (names and versions) from VCC **Manage Project**. [Contact us](#support)

## An outfit doesn't get wet {/* #outfit-dry */}

| Cause | Fix |
| --- | --- |
| The outfit is not registered. | Check whether the outfit is in the list in **RealWet > Outfit Management**. If it isn't, add it with **Find Now** or **Add Outfit Manually**. |
| **Use Wetness** is off on the outfit or part. | Turn on the check at the top of **This Outfit's Settings** and **Outfit Part Settings**. |
| It's a part away from the body, such as hair or a prop. | With **From Sweat Spots**, only areas near the start points get wet. It's normal for hair not to get wet. To make it wet, turn on the in-game **Whole Area** or add a [start point](./usage/wet-start-points.mdx) near it. |
| **Maximum Wet Range (%)** is low, or **This Material's Wet Look (%)** is 0%. | Check [Wetness settings](./usage/wet-settings.mdx#range) and the part's slot card. |
| The shader is not supported. | The part card shows **RealWet does not support this shader (…), so this part does not get wet.** See [Compatibility](./compatibility.mdx#shaders). |
| It is dry only in builds. | Look at the warning in the NDMF results window. See [NDMF warnings](#ndmf-warnings). |
| The whole uploaded avatar has no effects. | See [Uploaded without purchase activation](#not-activated). |

On **No See-Through** outfits, it is normal that the body doesn't show through. Please check the wetness by whether the color and gloss change. Protection regions don't block wetness; they block only the see-through.

## Only some parts don't get wet {/* #partly-dry */}

| Cause | Fix |
| --- | --- |
| The spot is out of sweat's reach (sleeve ends, skirt hems and so on). | This is normal. Raise the range, add a start point near it, or use **Whole Area**. |
| It's loose fabric far from the body. | Switch that part's **Fit Preset** to **Tight**. |
| Only that part's material uses an unsupported shader. | That part keeps its original look. Switch to a supported shader, or leave it as it is. |
| Only materials switched by a wardrobe animation stay dry. | Add that material to **This Outfit's Settings > Troubleshooting > Additional Replacement Materials**. |
| An optimization tool merged or copied parts. | **RealWet: only some outfit parts remain dry** appears in the NDMF results window. See the table below. |
| You moved one piece of the outfit out of the outfit root. | Move it back under the outfit root and it gets wet again. When you build, the Console shows the name of the moved piece. |

## Wet in the preview, dry in the build, Play or upload {/* #preview-ok-build-dry */}

If clothes get wet in the preview but not in Build & Test, Play or the upload, another tool or the environment usually changed the result during the build. Please look for the cause in this order.

1. After the build or Play, look at the NDMF results window. If it is closed, open it with **Tools > NDM Framework > Show NDMF Console**. For each outfit or part that <ProductName /> left without wetness, a warning starting with `RealWet:` gives its name and the reason. The full error text is in the Console.
2. Find the matching case in the table below and check the page on the right.

| Where it stays dry | Common cause | Where to look |
| --- | --- | --- |
| Only the uploaded avatar has no effects at all. The preview and Play look fine | This PC isn't activated. There is no NDMF warning, only one line in the Console. | [Uploaded without purchase activation](#not-activated) |
| Some outfits are dry only in Play | Some outfits aren't prepared yet, or the avatar was off when Play started. | [Some outfits don't get wet in Play](#play-not-ready) |
| Some lilToon parts are dry only in the upload (with PCSS4VRC) | PCSS4VRC replaced the materials at the first build step. | [PCSS4VRC replaced the materials](#pcss) |
| Only outfits processed by an anti-ripping or polygon reduction tool are dry | That tool changed the outfit mesh. | [Tools that change outfit meshes](#mesh-tools) |
| Only parts that went through another tool are dry | Another tool created, copied, split or merged parts, or replaced or rewrote their materials, so <ProductName /> couldn't recognize them. | [Another tool changed the material during the build](#material-replaced); in [NDMF warnings](#ndmf-warnings): **RealWet: only some outfit parts remain dry**, **RealWet: a renderer was left without wetness because its outfit is unclear**, and the d4rk row |
| The wet materials or menu values are different on the uploaded avatar | A tool that runs at the very end of the upload (for example, VRCFury Parameter Compressor) changed the result. | In [NDMF warnings](#ndmf-warnings): **RealWet: a later upload step changed RealWet's output** |
| Only materials swapped by an animation, MA Material Setter or Material Swap are dry | That replacement material wasn't prepared. | **Additional Replacement Materials** in [Only some parts don't get wet](#partly-dry) |
| Only outfits with a certain Poiyomi version are dry | That shader version isn't verified yet. | [Unsupported or unverified shaders](#shaders) |
| The warning's reason says Unity was compiling or importing | When the build started, Unity was compiling scripts or importing assets, or another RealWet task was running. | Build again once it finishes. [NDMF warnings](#ndmf-warnings) |
| Clothes don't get wet in a Quest (Android) build | <ProductName /> is PC only. | [Compatibility](./compatibility.mdx#requirements) |

If nothing matches, please send the report copied with **Copy Diagnostic Report** together with the `RealWet:` lines from the NDMF results window. [Contact us](#support)

## Another tool changed the material during the build {/* #material-replaced */}

If an outfit is wet in the preview but dry after upload, another tool may have replaced or copied that outfit's material during the build. <ProductName /> only makes the materials you registered wet. It doesn't force a material made by another tool to be wet; it leaves it as it is. The build doesn't stop, and other outfits stay wet.

Find the cause like this.

1. Build once (or use Build & Test). Then select the avatar's `RealWet` object and click **Status > Troubleshooting > Copy Diagnostic Report** in the inspector.
2. Paste the report into a text editor. Under `[Recent RealWet console lines]` near the end, find the line with the name of the dry outfit or part. The line also names the material.
   - `Material 'Towel White_FSS' referenced by default on 'Bath Towel' slot 0 is unsupported`: the material that came in during the build uses a shader <ProductName /> doesn't support.
   - `Final material 'Shirt_clone' cannot be traced to captured material 'Shirt'`: it's a copy made during the build, so <ProductName /> can't confirm that it belongs to the outfit.
3. Compare that material name with the material on the part in the scene. If the name is different or has something added at the end (`_FSS`, `_clone`, ...), another tool changed the material during the build.

From 1.0.2, the warning in the NDMF build results also says which check didn't match (the mesh changed, the number of slots changed, the material is not a copy made during the build, and so on).

How to fix it:

- Find the tool that made that material, and turn it off or exclude that outfit (part) from it. Build again, and the original material gets wet.
- That tool's effect will no longer apply to that outfit. Choose which one you want.
- If you can't tell which tool it is, send the report through [Contact us](#support).

**Case: on an avatar that uses VRCFury, one whole outfit is dry after upload**

- **Symptom:** The NDMF results window shows **RealWet: some clothing remains dry** (while uploading, **RealWet: some clothing is uploaded without wetness**), and the reason says `No compatible Wet slot remains after final material and animation checks`.
- **Cause:** Read/Write was off on the outfit's FBX, so <ProductName /> couldn't record the outfit's slot layout. Because of that, it couldn't confirm that the material copy VRCFury made during the build belonged to that outfit. Avatar Compressor (LAC) was not the cause. LAC only renames the final material, so even if the name looks different in step 3, you don't need to turn LAC off.
- **Fix:** From 1.0.2, the outfit gets wet even with Read/Write off on the FBX. On 1.0.1 or earlier, select the outfit's FBX, turn on Read/Write in the Model tab of the Inspector, and press Apply.

## Wet spots or protection don't fit the avatar {/* #placement-mismatch */}

<ProductName /> is made to work on many avatars, but depending on the avatar's body shape and bone positions, the spheres it places automatically may not fit. In that case, please adjust their position and range yourself.

| Symptom | Fix |
| --- | --- |
| Odd spots get wet, or spots that should sweat stay dry. | Move the wet start point sphere near that spot in the Scene (W) and change its size (R). [Open the editor](./usage/wet-start-points.mdx#editor), [Common adjustments](./usage/wet-start-points.mdx#tips) |
| A protection region is off from the chest or groin, or is too small or too big. | Move (W), rotate (E) and resize (R) the protection region in the Scene. [Edit protection regions](./usage/see-through-protection.mdx#editing) |
| The wet start points around the chest or the chest protection regions are off from the chest (the wrong breast bones were found). | Drag this avatar's breast bones into the **Left breast anchor** and **Right breast anchor** fields of **1. Body meshes** in the setup window. On an avatar that is already installed, check **Move the chest start points and chest protection to the new bones** and press **Update**. [Body meshes](./tutorial.mdx#body) |
| On an avatar shrunk or re-proportioned with bone scale, the chest start points or the chest protection regions are off (a layout placed with 1.0.2 or earlier). | 1.0.3 fixed where new ones are placed. Saved positions don't change when you update, so place them again with the reset steps in the last row below. |
| You want to fix the left and right sides together. | Both editors have **Symmetry**. Turn it on and edit one side only. |
| You want to go back to the original layout. | For start points, use [Reset and re-layout](./usage/wet-start-points.mdx#reset). For protection regions, use [Reset buttons](./usage/see-through-protection.mdx#reset). |

- After a change, please check the preview at 50% and 100%.
- Please check protection from the front, side and back, as in [How to check](./usage/see-through-protection.mdx#checking).
- When the wet start mode is **From Where It Touches the Body**, start points are not used, so moving a sphere doesn't change where clothes get wet. The same is true while the in-game **Whole Area** is on.

## Layered clothes vanish or draw in the wrong order {/* #layer-issues */}

See-through wet clothes look natural only when the body, underwear and outer clothes are drawn in the right order (render queue). <ProductName /> looks at how each outfit's parts overlap and sets the order automatically, but it can't detect every layer. Parts it misses can end up on the same queue or in reverse order, and then the inner clothes may seem to vanish when wet.

First, open the outfit's **This Outfit's Settings > Outfit Parts > Outfit Render Queue**. [Layer order](./usage/outfit-settings.mdx#layer-order) explains how to use it. Then find the case below that matches.

### Underwear in the same outfit vanishes at some angles {/* #layer-same-queue */}

- **Cause:** Two parts that touch or overlap share one queue. Unity then picks which one draws first, so the inner one can vanish when wet. This happens when parts cross each other, sit too close, or there are so many parts that there isn't enough evidence to decide.
- **How to tell:** The order list shows a **same queue** mark. After a build, **RealWet: check the clothing draw order** appears in the NDMF results window. If the layer wasn't detected, there may be no mark and no warning.
- **Fix:** Drag one of the two parts in the list so the inner part is higher and the outer part is lower. Use the same fix even when there is no mark.
- A material that draws the same mesh again, such as a hair shadow, is placed right after its base automatically. If the shadow is a separate object, drag it below its base in the list.

### Inner clothes vanish under a jacket or hair registered as a separate outfit {/* #layer-other-outfit */}

- **Cause:** Order is set for each outfit separately. Separate outfits are not ordered against each other, so a jacket registered on its own may be drawn before the clothes under it. The same applies to a jacket you turn on and off with a wardrobe if it is registered as another outfit.
- **Fix:** Switch the jacket outfit's slots to **Manual: Set Draw Priority** and give them a high number (for example, 20), or register the jacket together with the clothes under it as one outfit.
- Within one outfit, parts that are off at upload and turned on in game get the same order too.
- If an avatar's base clothes are registered mesh by mesh, see [Group an avatar's base clothes into one outfit](./usage/outfit-settings.mdx#group-base-clothes) to group them into one outfit.

### It looks wrong only after a material swap or an optimizer {/* #layer-swapped */}

- **Cause:** A material swapped by an animation, MA Material Setter or Material Swap keeps the original order when its render mode (opaque or cutout, or transparent) is the same as the original. If the render mode differs, it is placed at the start of its rendering band. When an optimizer changes a part so RealWet can't tell which original part it is, that part is also placed at the start. When parts with different orders are merged, the merged part uses the innermost of their positions.
- **How to tell:** If an optimizer is the cause, after a build the NDMF results window or the Console shows lines with the part name, such as **its material now uses another rendering band**, **RealWet could not tell which original part this is** or **It uses the innermost of their positions**.
- **Fix:** Please give the replacement material the same render mode as the original. Check the swapped state in Build & Test too, and if a warning says a part now shares a queue with another, drag it in the order list. If only the replacement material stays dry, see [Only some parts don't get wet](#partly-dry).

### A slot uses Preserve Material Queue {/* #layer-preserve */}

- **Cause:** **Preserve Material Queue** is an older setting. It doesn't calculate an order and uses the wet copy's base queue as it is. Opaque and cutout clothes all get the same queue (2460), so Unity decides the front-to-back order of overlapping parts. No build warning appears in this case.
- **How to tell:** If every slot of the outfit uses this setting, the order list shows **Every slot of this outfit keeps its material queue (an older setting).**
- **Fix:** Press **Use automatic order**, or switch the slot to **Automatic from Clothing Surfaces**. You can undo it with Ctrl+Z.

### Different rendering bands can't be ordered {/* #layer-bands */}

- **Cause:** Opaque or cutout clothes and transparent clothes are drawn in different bands. <ProductName /> does not move parts into another band. So if the inner clothes are transparent and the outer clothes are opaque, the inner clothes may be drawn later. When the body or skin sweat queue is close to 2499 and there is no room left for the clothes, the parts also keep their original queues.
- **How to tell:** The NDMF results window shows **…'s rendering band draws later** or **There is no room after the body/sweat … so these parts kept their previous queues**.
- **Fix:** <ProductName /> does not change your original materials or the body. Whether to match the two clothes' render modes is your choice. You can also use **Direct: Set Render Queue** on that slot, but a number in another band can change depth and shadows, so please check it in the preview.

### Overlap with parts not registered in RealWet {/* #layer-unmanaged */}

- **Cause:** <ProductName /> doesn't change the order of parts that aren't registered (stockings, lace and so on). If such a part's queue is below 2460, the wet clothes are drawn after it. The order list shows this as **(after …, which RealWet does not change)**. If it is 2460 or higher, the order is not matched, so the part may vanish under the wet clothes or show on top of them.
- **Fix:** Register that part in the same outfit, and it gets ordered together. If you don't need its wet look, set **This Material's Wet Look (%)** on that slot to 0%.

### Other clothes look wrong after changing the render queue {/* #layer-side-effects */}

:::caution[Changing a render queue can change how other clothes look]
The render queue is the drawing order for the whole avatar. When you change the numbers of one outfit, decorations, transparent effects and other outfits drawn before or after it can also layer differently.

- <ProductName /> does not change the render queue of your original materials. It changes only the queue of the wet copies used for the preview and upload. But the game draws those copies, so the visible order does change.
- An outfit whose creator relied on render queue numbers for its look (stencils, lace, transparent effects and so on) can look different when the order changes. The automatic order also sets new numbers for the wet copies.
- When you set a manual or direct number, the automatic parts of the same outfit skip that number, so other parts' numbers can move too.
- Manual numbers are counted on the same scale for outfits that use the same body. A high number draws after the parts of other outfits.
- Dragging and **Direct: Set Render Queue** set fixed numbers. They don't follow later changes to the body or RealSweat.

After a change, please check the front, side and back in the preview. Switch any slot you didn't want changed back to **Automatic from Clothing Surfaces**. You can reset a whole outfit at once with **Reset Clothing Order to Automatic**. For an outfit that must keep the order of its creator's numbers, turn off **Inside → outside detection first** on the same screen. Then the original material queue order comes first, and only equal queues are split by inside and outside. You can also use **Preserve Material Queue** on a single slot that must keep its creator's number, such as a transparent effect material. Please don't use it on opaque or cutout clothes.
:::

## NDMF warnings {/* #ndmf-warnings */}

<ProductName /> never stops a build. Only the parts it could not apply wetness to are uploaded with their original dry materials, and a warning is left in the NDMF results window. The full error is in the Unity Console. Your saved wet settings and original materials don't change, and RealWet tries again on the next build.

{/* SHOT U27: NDMF window with a RealWet warning */}

| NDMF warning | Meaning | What to do |
| --- | --- | --- |
| **RealWet: some clothing remains dry** (while uploading, **RealWet: some clothing is uploaded without wetness**; during Play, **RealWet: some clothing is shown without wetness in this Play**) | Only the named outfits are uploaded without wetness and without rain. The other outfits are fine. | Look at the reason in the warning. If Unity was compiling when you built, build again after it finishes. If you can't tell the reason, copy the diagnostic report and contact us. |
| **RealWet: only some outfit parts remain dry** | Another tool created, copied, split or merged parts, or an animation switches to a material that doesn't get wet. Only that part (or that state) is dry. | Check the settings of the tool named in the warning. If an optimizer merged several outfits into one mesh, leave that mesh out of the merge or group them as one outfit. |
| **RealWet: some parts may appear magenta (pink) to everyone** | Some parts can't be put back to their original materials. RealWet doesn't hide them; it leaves them as the build left them. | See [Pink materials](#pink). |
| **RealWet: Poiyomi … has not been verified yet** | The structure of the installed Poiyomi differs from what <ProductName /> knows. Outfits using that shader are built dry. | You can use this build as it is. Wait for a <ProductName /> update, or use a verified Poiyomi version. |

## Pink materials {/* #pink */}

| Cause | Fix |
| --- | --- |
| The original material itself has no shader (Missing) or is pink. | This is unrelated to <ProductName />. First install or restore the shader the outfit creator specified. |

## Uploaded without purchase activation {/* #not-activated */}

If you upload from a PC that is not activated, the <ProductName /> effects are quietly left out of the upload. The build doesn't fail, and no window appears.

- A notice and an **Open activation window** button appear right below the Avatar field of the setup window.

## PCSS4VRC replaced the materials {/* #pcss */}

On avatars that use PCSS4VRC, PCSS4VRC replaces lilToon materials with `_pcss` materials in the first build step. So parts that are wet in the preview may not be wet in the upload.

- For these parts, a **This part does not get wet when uploaded** notice and a button to turn the feature on right away appear above the outfit or part preview, and a single NDMF warning reports it when you build.
- **Fix:** In **Advanced settings > Experimental** in the setup window, turn on **PCSS4VRC (lilToon)** support and press **Update**. PCSS outfits then get wet too. It is an experimental feature, so please read [Advanced features](./advanced.mdx#experimental) first.
- Parts that use lilToon custom shaders, which PCSS4VRC doesn't replace, get wet in the upload too.
- Even with the feature on, parts whose lilToon **Multi** or **MultiOutline** (and Tessellation or Lite) materials PCSS4VRC replaces stay dry, and an NDMF warning appears. In 1.0.0 the warning may tell you to turn the feature on; if it is already on, this family is the reason. Switch that material to a standard lilToon shader, or leave it out of PCSS4VRC's conversion.

## lilSSRT shaders left in an old folder {/* #lilssrt-old-folder */}

- **Symptom:** lilSSRT outfits stay dry even with the lilSSRT experimental feature on. In 1.0.1 and earlier, the **Experimental** card of the setup window or the notice above the preview says **The installed lilSSRT has a different structure, so RealWet cannot make it wet**. From 1.0.2, it says **lilSSRT was found in …, not in its own folder …**, with the folder it found and the steps to fix it. The build doesn't stop.
- **Cause:** When a newer lilSSRT is imported over an older one, its shaders stay in the old folders (`Shaders/SSRTAO`, `Shaders/XeGTAO`) instead of their own folders.
- **Fix:**
  1. In the Project window, delete the folders `Assets/MeltzzZ/lilSSRT/Shaders/SSRTAO` and `Assets/MeltzzZ/lilSSRT/Shaders/XeGTAO` (whichever exist).
  2. Import the lilSSRT 1.4.3 package again.
  3. Right-click the `Assets/MeltzzZ/lilSSRT` folder and choose **Reimport**.
  4. Build again.

When PCSS4VRC (lilToon) is outside its own folder, 1.0.2 shows the folder it found and the steps to fix it in the same way.

## lilToon's shader importer is turned off {/* #liltoon-importer-off */}

- **Symptom:** Every lilToon outfit is built dry. Outfits that use other shaders get wet as usual, and the build doesn't stop. From 1.0.3, the NDMF build results show **RealWet: lilToon's shader importer is turned off in this project (LILTOON_DISABLE_ASSET_MODIFICATION)**, and the Inspector of the `RealWet` object, the outfit and the part shows a notice too. In 1.0.2 and earlier, the notice says the lilToon version **has not been verified yet**.
- **Cause:** The project sets `LILTOON_DISABLE_ASSET_MODIFICATION` (in **Scripting Define Symbols** or **Additional Compiler Arguments** under **Project Settings > Player > Other Settings**, or in a `csc.rsp` file). With it, lilToon doesn't import `.lilcontainer` shader files, so <ProductName />'s lilToon shaders are not created.
- **Fix:**
  1. Press **Remove it from the settings and make lilToon clothing wet** on the notice in the Inspector. It shows where the define is set and what changes when it is removed, and asks you.
  2. If you press **Remove**, only this define is removed from the places it found, and the scripts compile again. Other values and lines stay as they are, and `csc.rsp` is backed up to `Library/RealWet` before it is changed. **Keep as is** changes nothing.
  3. After the scripts finish compiling, build again. If lilToon outfits still stay dry, right-click the <ProductName /> `LilToon` shader folder named in the notice in the Project window and choose **Reimport**.

- You can also remove it yourself. Remove only `LILTOON_DISABLE_ASSET_MODIFICATION` from the places named in the notice and wait until the scripts finish compiling.
- Removing it lets lilToon adjust its shader settings around builds again (that is what this define turns off). If you or another tool added this define on purpose, that tool may expect it.
- <ProductName /> never asks or changes this setting by itself. It opens no window during a build, a preview or Play.

## lilToon outfits stay dry and (Failed To Load Script Object) appears {/* #liltoon-script-object */}

- **Symptom:** In 1.0.2 and earlier, every lilToon outfit is built dry and a notice says the lilToon version **has not been verified yet**. When you select one of <ProductName />'s lilToon shader files (`.lilcontainer`) in the Project window, the top of the Inspector shows `(Failed To Load Script Object)`. lilToon itself works as usual.
- **Cause:** Another asset in the project owns the GUID of lilToon's importer script, so Unity gave lilToon's importer script a new GUID. Up to 1.0.2, <ProductName /> looked for the importer by that GUID only.
- **Fix:** Please update <ProductName /> to 1.0.3 or later. From 1.0.3, lilToon outfits get wet in such a project too. You don't need to fix any file in the project, and <ProductName /> doesn't change your project's files either. If `(Failed To Load Script Object)` still shows in the Inspector, it doesn't affect the wetness.

If lilToon outfits still stay dry after updating, please send the report copied with **Copy Diagnostic Report**. It says where lilToon's importer was found. [Contact us](#support)

## VRCFury is too old {/* #vrcfury-old */}

In <ProductName /> 1.0.1 and earlier, on avatars that use VRCFury 1.1258 or earlier, every uploaded outfit stayed dry and the build showed an error that mentions `SweatAmount`. 1.0.2 fixed this.

**Fix:** Please update <ProductName /> to 1.0.2 or later. If you use VRCFury, please use **1.1436.0 or later**. Avatars without VRCFury are not affected.

## Tools that change outfit meshes {/* #mesh-tools */}

Tools that change the vertex order, the submeshes or the mesh structure of outfit meshes during the upload may not be compatible with <ProductName />. Anti-ripping tools and polygon reduction tools are examples.

- <ProductName /> fits its wetness data to the outfit meshes. If another tool changes a mesh so that the data no longer matches, that outfit or part goes up dry, without wetness.
- The build doesn't stop. The NDMF build results window shows the outfit (or part) name and the reason as a warning.
- AAO (Avatar Optimizer), d4rk Avatar Optimizer and TexTransTool are supported. Please see [Compatibility](./compatibility.mdx#optimizers).
- To make that outfit wet, please leave the wet outfits out of that tool, then build again.

## You installed the RealWet internal module in Poiyomi {/* #poi-internal-module */}

The **Third Party** list in a Poiyomi material's inspector (**Poi > Installed Modules** in older Poiyomi 11) shows `RealWet internal, do not install`. <ProductName /> uses this module to make its wet shaders, so it appears in the list. This is normal. Don't install it. If you do, <ProductName /> code goes into Poiyomi's own shaders, and <ProductName /> builds the outfits on those shaders dry. The build doesn't stop.

If you already installed it, undo it like this.

- **Poiyomi with the Third Party list**
  1. Select a Poiyomi material.
  2. In the inspector, open the **⋮** menu on the right of the **Third Party** header.
  3. Click every item that starts with **Remove RealWet**. Poiyomi rebuilds that shader.
  4. For each other Poiyomi shader you use, select one material that uses it. Poiyomi rebuilds that shader too.
- **Poiyomi with the Poi > Installed Modules menu**
  1. Open **Poi > Installed Modules** from the top menu.
  2. Untick `RealWet internal, do not install` (older name: `Cooki Clothing Wetness`).
  3. Click **Apply & Rebuild Shaders**.

Build again, and the Poiyomi outfits get wet again.

## The first build takes a long time {/* #long-first-build */}

On the first build or the first preview, RealWet creates the wet shaders and Unity compiles them. An avatar with many materials can take **tens of minutes**. During this time, the Unity window barely moves, so it can look frozen.

{/* SHOT U28: build progress bar */}

1. **Please wait.** During the upload, the progress bar shows the step, the count and the outfit name, such as `RealWet: Calculating outfit shape (3/22) · outfit name`. While Unity itself compiles shaders, the progress bar may stay the same for a long time, and the work can also go on without any window.
2. **Check the CPU in Task Manager.** If Unity or `UnityShaderCompiler` is using the CPU, it is still working. Please don't close it; wait.
3. Treat it as frozen only when the CPU stays near 0% for several minutes and the progress bar doesn't change. In that case, please note the first red error in the Console and how long you waited, and contact us.

- From the second build on, the shader cache made in the first build is reused, so it is much shorter.
- It takes longer when the PC is busy, such as while streaming or recording. It's best to do the first build ahead of time, while the PC is idle.
- You can prepare ahead of the build with **RealWet > Outfit Management > Prepare Needed Outfits**.
- A progress bar also appears for **Install** and **Update** in the setup window, and the first time you enter Play. While it shows the current step, please wait.

For typical times, see [Performance](./performance.mdx#build-time).

## The first upload takes a long time {/* #first-upload */}

The first upload takes long because, on top of the same shader preparation as the first build, the VRChat SDK compiles shaders and compresses the upload file.

- Each wet material includes wet shaders, so the upload file gets bigger and compression takes time too. See [Performance](./performance.mdx#upload-size).
- The time Poiyomi takes to lock materials during upload is added too.
- From the second upload with the same settings, it gets shorter.
- The first upload after you update <ProductName /> can take a long time too. The first upload after updating to 1.0.3 compiles the wet shaders again once, so on an avatar with many outfits it can take about 20 minutes. Even if the progress display doesn't move, please don't close Unity while it is using the CPU.

## The Hold on window {/* #hold-on */}

Unity's **Hold on** window means Unity is asking you to wait until it finishes its work.

| When | Cause and fix |
| --- | --- |
| The first preview, the first build, right after a shader update | The wet shaders are being prepared. Please wait. |
| Right after importing a package | Unity is importing scripts and shaders. Please wait. |
| While Unity is in front and you're doing nothing | <ProductName /> prepares ahead only while Unity is in the background. If the window still appears, it may be work by another tool or by Unity itself. |
| When you come back to Unity from another app | It is the short moment while the advance preparation stops. Shader preparation that can't be interrupted midway starts only when Unity has been in the background for more than 3 minutes. |

If **Hold on** keeps appearing for a long time on the same action, please note that action and the Console contents, and contact us.

## The menu or parameters go over the limit {/* #over-limit */}

VRChat allows up to **256 bits** of synced parameters per avatar. The <ProductName /> recommended menu is 87 bits (88 bits on an avatar that also uses RealSweatSystem). If the total goes over the limit together with RealSweatSystem or other tools, the VRChat SDK blocks the upload.

1. Check how much <ProductName /> uses in **Runtime Parameter Cost** in **RealWet > In-Game Menu**.
2. Uncheck dials you don't use. Each dial is 8 bits, and each toggle is 1 bit. For example, removing **Spread Wetness Wider**, **Wet Edge** and **Wet Appearance** saves 24 bits.
3. Press **Apply / Update Runtime Menu** and build again.

- Features whose buttons you removed keep working with the values set in Unity.
- One menu page has 8 slots. When there aren't enough slots, <ProductName /> creates a **Next** page and doesn't add to the main menu.
- If you run short, we recommend using the Parameter Compressor of VRCFury 1.1436.0 or later together with it. If the compression tool changes the wet parameters, the NDMF results window tells you.

## The menu is missing {/* #menu-missing */}

1. Look for **Wet** in the main menu (**젖음** in Korean, **濡れ** in Japanese).
2. If you moved the menu, look inside the menu set in the **MA Menu Installer** on the `RealWet` object.
3. In **RealWet > In-Game Menu**, press **Apply / Update Runtime Menu**.
4. Build again and check that avatar. If the build failed, you may be looking at the previous avatar.

- If the menu files are gone, <ProductName /> recreates and reconnects them when you open a saved scene. A notice at the top of the `RealWet` object's Inspector says **RealWet's in-game menu file was missing, so RealWet made it again and linked it. Save the scene to keep it.**, and the Console shows the line `RealWet's in-game menu file was missing (…), so RealWet made it again and linked it. Save the scene to keep it.` Please save the scene.
- If you moved the menu yourself or replaced it with another menu, <ProductName /> leaves that menu alone. To recreate it, delete the **MA Menu Installer** on the `RealWet` object, then please press **Repair Runtime Menu** in the **In-Game Menu** tab.
- If the menu shows in another language, choose the language you want in Unity, update the menu, and please build again.
- If the menu buttons are there but the icons are missing, please import the package's `Icons` folder again, then update the menu. The features still work.

## Some outfits don't get wet in Play {/* #play-not-ready */}

## Texture limit {/* #texture-limit */}

On PC, Unity and VRChat can draw only up to 64 textures used by one shader pass. Poiyomi materials with many features turned on use the unlocked shader in the preview, so adding wetness can go over this limit.

- Those slots are previewed with their original look instead of turning pink, and a message appears.
- VRChat PC uploads lock the shader first, so these slots are usually uploaded wet.
- If the final shader in the upload also goes over the limit, only that material goes back to its original dry material. The upload doesn't stop.
- In 1.0.2 and earlier, on Poiyomi 10.0.20 and later and Poiyomi 11 parts that use both UV3 and UV4, a slot over the limit could not go back to its original material and could become invisible or pink. 1.0.3 fixed this.
- To keep the wetness, please reduce the texture features that material doesn't use (MatCap, emission, decals and so on), then build again.
